# /i18n - Internationalization & Localization Mode

$ARGUMENTS

## Purpose & Core Rule

Activates i18n mode for converting hardcoded user-facing strings into structured localization dictionaries and configuring multi-language support.

> **i18n = ZERO HARDCODED STRINGS, LOCALE-AWARE FORMATTING, CONSISTENT KEYS**

- Extract user-facing text from templates/JSX/HTML into structured translation files (`en.json`, `vi.json`, etc.).
- Enforce standard formatting for currency, dates, numbers, and plurals via native `Intl` APIs.
- Maintain key hierarchy and ensure 100% translation completeness across all supported locales.

---

## When to Use

- **Use when:** Adding multi-language support, scanning for unextracted strings, synchronizing translation keys, formatting dates/currencies per locale, or handling RTL layouts.
- **Do not use:** Translating internal error logs, code identifiers, database column names, or API payloads.

---

## Supported Intents

```text
/i18n extract all hardcoded strings in src/components
/i18n add vietnamese locale
/i18n sync translation keys between en and vi
/i18n format currency and dates in checkout
/i18n check missing translation keys
```

---

## i18n Dimensions & Best Practices

| Dimension | Rule & Standard |
| :--- | :--- |
| **1. Key Naming** | Use hierarchical, domain-based kebab-case or dot-notation (e.g. `auth.login.submit-btn`). |
| **2. Dynamic Variables** | Use named interpolation `{userName}` instead of string concatenation (`"Hello " + name`). |
| **3. Pluralization** | Use ICU MessageFormat standard (`{count, plural, =0{No items} one{1 item} other{# items}}`). |
| **4. Date & Numbers** | Use standard `Intl.DateTimeFormat` and `Intl.NumberFormat` instead of hardcoded formats (`dd/mm/yyyy`). |
| **5. RTL & Layout** | Use logical CSS properties (`margin-inline-start`, `text-align: start`) for RTL compatibility. |

---

## Execution Protocol

### Phase 1: Scan & Detect Hardcoded Strings
- Scan JSX/HTML templates and UI strings. Distinguish user-facing text from technical constants/identifiers.

### Phase 2: Design Key Hierarchy
- Organize keys by domain/feature (e.g., `common.*`, `checkout.*`, `errors.*`). Avoid duplicate keys with conflicting meanings.

### Phase 3: Extract & Replace in Code
- Replace literal text with translation hooks/functions (e.g. `t('checkout.pay-now')`, `<Trans>`).

### Phase 4: Populate Locale Dictionaries
- Update default locale (e.g. `en.json`) and target locales (`vi.json`, `ja.json`). Mark untranslated keys with fallback tags.

### Phase 5: Currency & Date Formatting Normalization
- Replace raw `.toFixed(2)` or custom date splitters with locale-aware formatters.

### Phase 6: Missing Key & Parity Audit
- Run audit script/check to verify all keys present in `en.json` exist in all target language files.
